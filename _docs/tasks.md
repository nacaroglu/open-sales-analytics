# Sales Analytics — Task Backlog

Tasks are ordered so a fresh contributor can pick any one, read only its own description, and finish it in a single session. Where a task depends on artifacts from an earlier task, the dependency is named explicitly in the description.

Stack (locked): FastAPI + DuckDB backend, Vite + React + TypeScript + Recharts + Tailwind frontend, Playwright for the single browser test, single multi-stage Docker image.

---

## 1. Bootstrap repository with a passing test
Goal: Create the empty monorepo layout with one trivial passing test in CI.
Description: Initialise a git repository containing `backend/` and `frontend/` directories, a top-level `README.md`, and a `.gitignore`. Add a single Python test in `backend/` (e.g. `test_smoke.py` asserting `True`) runnable with `pytest`, and a GitHub Actions workflow that installs Python and runs it. No application code yet.

## 2. Backend project skeleton with health endpoint
Goal: Stand up a runnable FastAPI app exposing `GET /api/health`.
Description: In `backend/`, add `pyproject.toml` (or `requirements.txt`) with FastAPI, Uvicorn, DuckDB, and pytest. Create an `app` package with a minimal FastAPI application and a `/api/health` route returning `{"status": "ok"}`. Add a pytest that uses `httpx.AsyncClient` (or `TestClient`) to assert the endpoint responds 200.

## 3. Frontend project skeleton with a rendered page
Goal: Stand up a Vite + React + TypeScript app that renders a placeholder page.
Description: In `frontend/`, scaffold a Vite React-TS project, add Tailwind CSS, Recharts, TanStack Query, and Vitest with React Testing Library. Replace the default page with a single component that renders the product name. Add one Vitest test that renders the component and asserts the product name is present.

## 4. Backend configuration module
Goal: Centralise runtime config driven by environment variables.
Description: Add a `config.py` in the backend that reads `DATASET_DIR`, `DATASET_TTL_HOURS` (default 24), `MAX_UPLOAD_BYTES` (default 50 MB), `MAX_ROWS` (default 500_000), and `PUBLIC_DEMO_MODE` (default false). Expose a typed settings object (Pydantic Settings). Add tests that verify defaults and overrides via environment variables.

## 5. Canonical DuckDB schema
Goal: Define the per-dataset DuckDB schema and a helper to create a fresh dataset file.
Description: Add a module that, given a path, creates a DuckDB file with a `line_items` table (six typed columns using `DECIMAL(18,4)` for `unit_price`) and a `dataset_meta` table (id, currency, created_at, expires_at, token_hash, row_count). Include a function to open an existing dataset file read-only. Test that creation is idempotent-per-path and that the schema matches expectations.

## 6. Deterministic synthetic sample dataset generator
Goal: Produce a reproducible sample CSV satisfying the dataset contract.
Description: Write a script (e.g. `scripts/generate_sample.py`) that, given a fixed seed, emits a CSV with roughly 10,000 orders over 12 months, 25–50 products, uneven popularity, weekly/seasonal patterns, and price variation. Commit the generated CSV under `backend/app/sample/`. Add a test that hashes the generated bytes to assert determinism.

## 7. CSV header and file-limits validation
Goal: Reject uploads that violate structural limits before row validation runs.
Description: Add a validator that inspects a CSV file for byte size, row count (streamed), UTF-8 decoding, presence of the six required headers, and identification of extra columns (warning only). Return a structured result object (errors, warnings). Cover each rule with a unit test using small in-memory CSVs.

## 8. Row-level validation via DuckDB staging
Goal: Validate all row-level rules using DuckDB SQL against a staging table.
Description: Load a CSV into an in-memory DuckDB staging table with all columns as `VARCHAR`, then run SQL checks for missing values, non-parseable dates, future dates, non-positive quantity, negative price, and zero-price warnings. Emit a structured list of `{row_number, field, code, reason}`. Test each rule with fixture CSVs (one bad row per fixture) and one all-clean fixture.

## 9. Cross-row uniqueness and product-name consistency
Goal: Detect duplicate `(order_id, product_id)` pairs and conflicting product names.
Description: Extend the staging-table validator with two SQL checks: a uniqueness check on `(order_id, product_id)` and a consistency check that one `product_id` maps to one `product_name`. Return the offending row numbers and both conflicting names where applicable. Add fixture-driven tests for both rules and for a clean multi-line-order case.

## 10. Import pipeline: staging to canonical
Goal: Move a validated dataset from staging into a fresh per-dataset DuckDB file.
Description: After validation succeeds, transform staging rows into properly typed rows (dates, integers, decimals) and insert them into the canonical `line_items` table produced by task 5. Populate `dataset_meta` with id, currency, timestamps, and row count. Delete staging state and the raw CSV on both success and failure. Test the success path and a failure-during-insert path (no residue).

## 11. Dataset ID and bearer token issuance
Goal: Generate unguessable dataset IDs and bearer tokens with hashed storage.
Description: Add a small module that produces a URL-safe dataset ID and a separate bearer token via `secrets.token_urlsafe`, and computes a SHA-256 hash of the token for storage in `dataset_meta`. Provide a `verify_token(dataset_id, presented_token)` helper that reads the hash and returns a boolean in constant time. Unit-test issuance uniqueness and verify/reject cases.

## 12. `POST /api/datasets` upload endpoint
Goal: Wire the upload flow end-to-end behind one HTTP endpoint.
Description: Accept a multipart CSV upload with a `currency` form field, enforce request size, run validation (tasks 7–9), on success run the import (task 10), issue token (task 11), and return `{dataset_id, token, meta, initial_summary}`. On failure return a structured error envelope with bounded error list and total count. Integration-test one success and one representative failure.

## 13. `POST /api/datasets/sample` endpoint
Goal: Create a temporary dataset from the bundled sample with no upload.
Description: Load the bundled sample CSV (from task 6) through the same import pipeline used by `/api/datasets`, issue a token, and return the same response shape. Ensure this endpoint remains enabled in public-demo mode. Add one integration test asserting a 200 and a queryable dataset.

## 14. Bearer-token authorization dependency
Goal: Protect dataset-specific endpoints with a reusable auth dependency.
Description: Add a FastAPI dependency that extracts the `Authorization: Bearer` header, loads the dataset metadata by ID, checks expiry, and calls the verifier from task 11. Return 401 on missing/invalid token and 404 on missing/expired dataset. Unit-test each rejection branch and one accepted case.

## 15. `GET /api/datasets/{id}` metadata endpoint
Goal: Return non-sensitive dataset metadata for an authorised caller.
Description: Behind the auth dependency (task 14), return `{id, currency, created_at, expires_at, row_count, date_range: {min, max}}`. Do not include token or file paths. Test authorised success, unauthorised, and expired responses.

## 16. Analytics: KPI queries
Goal: Compute the four KPI values for a given date range.
Description: Add pure functions/SQL that, given a dataset connection and `[start, end]`, return gross sales, distinct order count, units sold, and AOV (zero when no orders). Use `DECIMAL` arithmetic throughout. Unit-test with a tiny hand-written dataset covering multi-line orders and varying prices.

## 17. Analytics: automatic-granularity trend bucketing
Goal: Aggregate gross sales into daily/weekly/monthly buckets based on range span.
Description: Add a function that picks granularity from the active `[start, end]` (≤90d daily, ≤2y weekly, else monthly) and returns `{granularity, buckets: [{bucket_start, gross_sales}]}`. Emit contiguous bucket starts even when a bucket is empty. Unit-test the three thresholds and empty-bucket behaviour.

## 18. Analytics: top-products ranking
Goal: Rank products by gross sales for a date range.
Description: Add a query returning the top N products (default 10) with `{product_id, product_name, gross_sales, units_sold, distinct_orders}`, ordered by gross sales descending with stable tiebreak by `product_id`. Unit-test tie handling and N smaller than the product count.

## 19. `GET /api/datasets/{id}/analytics` endpoint
Goal: Expose KPIs, trend, and top products through one authorised endpoint.
Description: Accept optional `start` and `end` query parameters (default to full dataset range), clamp to the dataset range, and return `{range, granularity, kpis, trend, top_products, currency}` by calling tasks 16–18. Reject inverted or out-of-range dates with 400. Add one integration test using the sample dataset.

## 20. `DELETE /api/datasets/{id}` endpoint
Goal: Let the current session delete its dataset early.
Description: Behind the auth dependency, delete the DuckDB file and metadata for the given dataset. Return 204 on success and 404 on missing. Add tests for authorised delete, unauthorised delete, and idempotent double-delete behaviour.

## 21. Expiry and cleanup job
Goal: Remove expired datasets on startup and periodically.
Description: On application startup, scan the dataset directory and delete any dataset whose `expires_at` has passed or whose metadata is unreadable. Schedule an `asyncio` task to repeat the sweep every N minutes (configurable). Add tests that seed an expired and a live dataset and assert only the expired one is removed.

## 22. Public-demo mode enforcement
Goal: Disable arbitrary uploads at the server when demo mode is enabled.
Description: When `PUBLIC_DEMO_MODE=true`, `POST /api/datasets` must return 403 without invoking validation, while `POST /api/datasets/sample` remains available. Log the rejection at info level without any request-body content. Test both endpoints in demo mode and normal mode.

## 23. Structured logging and secret redaction
Goal: Emit structured logs that never include sensitive data.
Description: Configure a JSON logger for the FastAPI app that records method, path, status, duration, and dataset ID (never token, filename, or row contents). Add a small redaction test that captures logs during an upload and asserts none of the forbidden fields appear.

## 24. Frontend: API client and session-token store
Goal: Provide a typed API client and a session-storage token holder.
Description: In `frontend/`, add a `lib/api.ts` with typed wrappers for each backend endpoint using `fetch` and TanStack Query, plus a small session-storage module that reads/writes the bearer token and dataset ID. Include a Vitest test using MSW (or fetch mock) that verifies the auth header is attached when a token is present.

## 25. Frontend: upload screen
Goal: Build the initial upload page with sample-load action.
Description: Add a page that shows the schema reference, a file input restricted to `.csv`, a currency selector, a **Try sample data** button, and visible 50 MB / 500,000-row limits. Wire the two actions to the endpoints from tasks 12 and 13 with a loading state. Component-test the render and both button behaviours with a mocked API.

## 26. Frontend: validation error and warning display
Goal: Render structured validation failures without leaving the upload flow.
Description: When the upload endpoint returns a structured error envelope, show a summary, a bounded list of `{row, field, code, reason}` rows, a total-error count, and any warnings. Never imply that a partial dataset was imported. Test with a fixture error payload covering multiple error types and warnings.

## 27. Frontend: dashboard shell and routing
Goal: Add a dashboard route that loads dataset metadata behind the stored token.
Description: Add a route `/d/:datasetId` that reads the token from session storage, calls the metadata endpoint (task 15), and renders dataset date range, currency, row count, and expiry. Include an **Analyze another file** action that clears session state and returns to upload. Test the loaded and unauthorized paths.

## 28. Frontend: KPI cards
Goal: Render the four KPI cards from the analytics endpoint.
Description: Build a `KpiCards` component that consumes the analytics response and renders gross sales, orders, units, and AOV with currency formatting. Handle the empty-range case (zeros). Component-test rendering and formatting.

## 29. Frontend: sales trend chart
Goal: Render the auto-bucketed trend using Recharts.
Description: Build a `TrendChart` component that takes `{granularity, buckets}` and renders a Recharts line or bar chart, clearly labelling the active granularity. Handle the empty-buckets case with a placeholder message. Component-test each of the three granularities.

## 30. Frontend: top products chart
Goal: Render the top-products horizontal bar chart with a compact table.
Description: Build a `TopProducts` component that renders a Recharts horizontal bar chart of gross sales for up to 10 products and a compact table showing units sold and distinct order count. Component-test rendering with fewer than 10 products and with ties.

## 31. Frontend: date-range filter
Goal: Let the user restrict the dashboard to a sub-range.
Description: Add start/end date inputs constrained to the dataset range with a reset action; on change, refetch analytics and update KPIs, trend, and top products consistently. Disable submission for inverted ranges. Component-test the constraint behaviour and the reset action.

## 32. Frontend: expired, unauthorized, empty, and error states
Goal: Handle the remaining UI states cleanly across pages.
Description: Add shared components/hooks so that expired datasets (410/404), missing tokens (401), empty date ranges, and generic API errors show meaningful messages and a path forward (usually back to upload). Cover each state with a component test.

## 33. Playwright end-to-end happy path
Goal: One stable browser test covering the golden flow.
Description: Add Playwright to the frontend, plus a script that starts the backend and frontend for the test. Write a single spec that loads the sample dataset, verifies KPI cards and both charts render, changes the date range, and asserts the values update. Run it in CI as a job that spins up the built container.

## 34. Multi-stage Dockerfile
Goal: Ship one image that serves the SPA and API from the same origin.
Description: Add a Dockerfile with a Node build stage for the frontend and a Python runtime stage that copies the built assets and mounts them under FastAPI as static files. Expose one port, include a healthcheck hitting `/api/health`. Add a `docker build` + `curl /api/health` smoke check to CI.

## 35. GitHub Actions pipeline
Goal: Run the full quality bar in CI on every push and PR.
Description: Extend the workflow to run backend tests, frontend tests, linting and type checks for both, the Playwright test against the built container, and the Docker build. Cache dependencies where sensible. The workflow must fail if any job fails.

Goal: Document how to run, configure, and operate the application.
Description: Write the top-level `README.md` with a one-command Docker run, the full environment variable reference, the dataset contract with valid/invalid examples, privacy behaviour, and known limitations (no horizontal scaling, best-effort restart survival). Include a short architecture note linking to `_docs/plan.md`.
