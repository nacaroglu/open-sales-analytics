Open Sales Analytics — небольшое самостоятельно размещаемое веб-приложение. Вы загружаете CSV с завершенными
товарными позициями продаж, а оно показывает валовые продажи, заказы, единицы товара, среднюю стоимость заказа,
тренд продаж и самые популярные товары за изменяемый диапазон дат. Валовые продажи — это сумма произведений
количества на цену единицы по строкам выбранного периода. Возвраты, скидки, налоги и доставка не учитываются.

## Запуск с Docker

Опубликованного образа нет, поэтому один раз соберите его из рабочей копии репозитория, а затем запустите:

```sh
docker build -t open-sales-analytics .
docker run -p 8000:8000 open-sales-analytics
```

Откройте <http://localhost:8000>. Появится экран загрузки; кнопка **Попробовать пример данных** откроет панель с примером файла.
`curl http://localhost:8000/api/health` возвращает `{"status":"ok"}`.

`/health/live` проверяет только, что процесс отвечает. `/health/ready` возвращает `200` и
`{"status":"ready","service":"open-sales-analytics","environment":"development","version":"local"}`, когда инициализация,
временное хранилище, DuckDB и встроенный пример готовы; иначе возвращается общий статус `503`. Поля `environment` и
`version` берутся из `OSA_ENVIRONMENT` и `OSA_VERSION`. Ни одна конечная точка не раскрывает имя хоста, путь, учетные данные
или секрет.

Контейнер работает от непривилегированного пользователя (UID 10001) и хранит наборы данных в `/data`
(`DATASET_DIR=/data`). Без тома они теряются при удалении контейнера. Чтобы сохранить их, подключите именованный том к `/data`:

```sh
docker run -p 8000:8000 -v osa-data:/data open-sales-analytics
```

С томом наборы данных сохраняются после `docker restart` и повторного создания контейнера по мере возможности, но
каждый из них по-прежнему истекает через `DATASET_TTL_HOURS`. Если вместо именованного тома подключить каталог хоста
к `/data`, он должен быть доступен для записи непривилегированному пользователю контейнера (UID 10001), например
`sudo chown 10001 /path/to/dir`.

Образ проверяет себя: через несколько секунд после запуска `docker ps` показывает `healthy`, а если `/api/health`
перестает отвечать — `unhealthy` (проверка каждые 10 s, тайм-аут 3 s, 3 сбоя, начальный период 10 s). `docker stop`
завершает сервер менее чем за секунду с кодом 0, предварительно остановив фоновую очистку. Сам сервер не задает
тайм-аут запроса (применяются значения uvicorn по умолчанию), поэтому очень медленная загрузка завершится лишь тогда,
когда клиент прекратит ожидание.

Передайте настройку через `-e`, используя переменную из [таблицы ниже](#настройка):

```sh
docker run -p 8000:8000 -e PUBLIC_DEMO_MODE=true -e OSA_ENVIRONMENT=production -e OSA_VERSION=20261024-123456-abc1234 open-sales-analytics
```

Пошаговый запуск с созданными тестовыми данными: от свежей рабочей копии до панели. Для шага 1 нужен

```bash

```

Команда записывает `backend/app/sample/sample_sales.csv`. Благодаря начальному значению генератора файл
детерминирован: все получают одинаковые данные и одинаковые числа на шаге 6. Выполните команду до `docker build`:
файл копируется в образ.

Проверьте первые строки:

## Сравнения

Карточка диапазона дат позволяет сравнить активный диапазон с предыдущим периодом или тем же периодом прошлого года.
Панель показывает точные даты из API. Сравнение полного диапазона недоступно, если сравниваемый период начинался бы
до первой даты набора данных. Для сравнений с високосным днем используется последний допустимый день февраля в году
сравнения. Если предыдущее значение отсутствует, показывается “Нет предыдущего значения”; два нулевых значения — “Без изменений”;
новый товар — “Новый”; в остальных случаях процент показывается как “Сопоставимо”.

## Аналитика товаров

Все показатели товаров используют выбранный включительный активный диапазон, если не указано иное. Денежный показатель
— валовые продажи: скидки, возвраты и себестоимость не входят в контракт набора данных. Каждое название и ID товара
показывается как предоставленный сервером текст.

| Подпись UI и ключ | Формула и знаменатель | Окно и нестандартные состояния | Пример расчета |
| --- | --- | --- | --- |
| Рейтинги — `gross_sales` | Сумма quantity × unit price; проданные единицы — сумма quantity; заказы — число уникальных заказов | Активный диапазон; в пустом диапазоне товаров нет | Строка с 2 единицами по 12.50 добавляет 25.00 валовых продаж |
| Доля валовых продаж — `gross_sales_share` | Валовые продажи товара / общие валовые продажи товаров | Активный диапазон; данных недостаточно, когда общие валовые продажи равны нулю | 15 из 100 — это 15.00% |
| Доля лучших 20% — `top_20_percent_share` | Валовые продажи лучших 20% по числу товаров / общие валовые продажи | Активный диапазон; данных недостаточно при нулевом итоге | Пять товаров 50/20/15/10/5: лучший один дает 50.00% |
| Товаров до 80% — `products_to_80_percent` | Минимальное упорядоченное число товаров, накопленная доля которых достигает 80% | Активный диапазон; данных недостаточно при нулевом итоге | 50+20+15 достигает 80% на 3 товарах |
| Накопленная доля — `cumulative_share` | Нарастающие валовые продажи / общие валовые продажи | Активный диапазон; недоступно при нулевом итоге | Первые три товара золотого примера дают 85.00% |
| Рост товара — `product_growth` | Текущие валовые продажи минус валовые продажи сравнения; процент использует значение сравнения | Период сравнения; `Новый`, `Нет текущих продаж`, `Без изменений` или недоступное сравнение не показывают вводящие в заблуждение проценты | Рост с 10 до 20 — это +10 и +100.00% |
| Рейтинг роста/падения — `rising_products`, `falling_products` | Рейтинг по абсолютному изменению валовых продаж | Выбранное сравнение; недоступно, когда сравнение недоступно | Изменение +10 стоит выше роста +900% с абсолютным изменением +1 |
| Неактивные товары — `dormancy` | Товары без продаж в выбранном окне 30, 60 или 90 дней; ранние итоги используют продажи до окна | Привязано к концу выбранного диапазона (последней дате набора для полного диапазона), по умолчанию 60; недостаточная история и нулевой результат различаются. Продажа ровно за N дней до привязки входит в окно | Товар, последний раз проданный за 60 дней до привязки, включается для окна 60 дней |
| Взвешенная цена единицы — `weighted_unit_price` | SUM(quantity × unit price) / SUM(quantity) | Интервалы активного диапазона; интервалы без продаж — пропуски, а не нулевые цены | 1 единица по 10 плюс 3 по 20 дает 17.50 |
| Проникновение в заказы — `order_penetration` | Уникальные заказы с товаром / все уникальные заказы | Активный диапазон; ноль заказов — нулевой результат | 25 из 200 заказов — 12.50% |
| Поддержка — `basket_support` | Совместные заказы / допустимые заказы-корзины | Активный диапазон; требуется не менее 10 совместных заказов и поддержки 0.1% | 10 совместных заказов из 10,000 дают 0.10% |
| Достоверность — `basket_confidence` | Совместные заказы / заказы с направляющим товаром | Активный диапазон; пары ниже порогов не показываются | A→B и B→A могут различаться из-за разного числа заказов |
| Лифт — `basket_lift` | Достоверность / поддержка целевого товара | Активный диапазон; пары ниже порогов не показываются | Лифт сравнивает наблюдаемую частоту пары с поддержкой целевого товара |

Общий реестр подписывает эти ключи так: Gross-sales share, Cumulative gross-sales share, Top 20% product share,
Products to 80% of gross sales, Product gross-sales growth, Rising products, Falling products, Dormant products,
Weighted realized unit price, Order penetration, Basket support, Basket confidence и Basket lift.

Пары ниже любого из порогов корзины не показываются, даже при высоком лифте. Заказы с более чем 100 уникальными
товарами исключаются только из анализа корзины; ровно 100 включаются, и эти заказы по-прежнему учитываются в рейтингах,
проникновении и валовых продажах. Вкладка Products сообщает число исключенных заказов. История цен описывает только
движение фактической цены; она не измеряет ценовую эластичность и не доказывает, что изменение цены вызвало изменение
продаж. Растущие и падающие товары определяются по абсолютному изменению, чтобы крошечные базовые значения не
доминировали. Проникновение, поддержка, достоверность и лифт используют уникальные заказы.

Документация API доступна по [`/docs`](http://localhost:8000/docs). `GET /api/datasets/{id}/overview` возвращает KPI
обзора и тренды; `GET /api/datasets/{id}/products` — анализ портфеля; `GET /api/datasets/{id}/products/detail?product_id=...`
— подробный анализ одного товара. Для конечных точек набора данных нужен его bearer-токен.

## Аналитика клиентов

Аналитика клиентов содержит только агрегаты. Она описывает идентифицированные заказы и никогда не показывает
идентификатор клиента, список клиентов или сумму отдельного клиента. Активный отчетный диапазон включает начальную и
конечную даты, если строка явно не описана как полная история до выбранной даты окончания. Примеры ниже используют
зафиксированный fixture `backend/tests/fixtures/customers/golden_customers.csv`: 20 заказов, 19 идентифицированных
заказов, 10 клиентов и 380.0000 идентифицированных валовых продаж от 2025-01-01 до 2025-09-30.

| Подпись UI и ключ | Формула, окно и привязка | Недостаточно данных и нулевой результат | Пример расчета |
| --- | --- | --- | --- |
| Покрытие клиентов — `customer_coverage` | Уникальные идентифицированные заказы / все уникальные заказы; считается по заказам для набора и выбранного диапазона | Без столбца `customer_id` недоступно, ниже 50% скрывается, при отсутствии заказов покрытие равно null | 19 / 20 = 95.0% в золотом fixture |
| Идентифицированные клиенты — `identified_customers` | Уникальные значения `customer_id` с идентифицированной строкой в активном диапазоне; начало и конец включаются | При отсутствии идентифицированных клиентов возвращается 0 с `zero_result` | В золотом диапазоне их 10 |
| Валовые продажи новых и вернувшихся клиентов — `new_vs_returning` | Разделение `SUM(quantity × unit_price)` по тому, относится ли строка к первой дате заказа клиента за всю историю или к более поздней; история учитывается до конца диапазона | Без идентифицированных строк возвращаются нулевые денежные значения с `zero_result` | Покупка CUST-01 от 2024-12-15 делает его продажи 2025 года повторными |
| Доля повторных покупок — `repeat_purchase` | Активные клиенты минимум с двумя уникальными заказами до выбранного конца / активные идентифицированные клиенты; заказы до начала диапазона учитываются | Без активных клиентов — `insufficient_data`; активные клиенты без повторов дают ровно 0 (`zero_result`) | Заказы в один день остаются разными заказами, а не разными датами |
| Дни между покупками — `days_between_purchases` | Медиана календарных дней между последовательными уникальными заказами; интервал включается, если поздний заказ входит в диапазон, а заказы в один день дают 0 | Без интервалов медиана null и `insufficient_data`; фиксированные интервалы: 0, 1-7, 8-14, 15-30, 31-60, 61-90, 91-180, 181-365 и 366+ | Пара в один день попадает в интервал 0 |
| Удержание когорты — `cohort_retention` | Удержанные клиенты / размер когорты привлечения за всю историю, по смещению календарного месяца; когорты используют всю историю до выбранного конца | Отсутствующие когорты — `insufficient_data`; правая крайняя ячейка — `Пока не наблюдалось`, а не 0% | Месяц 0 равен 100.0% для каждой непустой когорты |
| Историческая ценность клиента — `historical_customer_value` | Наблюдаемые идентифицированные валовые продажи до даты окончания / число идентифицированных клиентов; медиана — среднее значение в середине ряда значений клиентов; кривые когорт используют накопленные продажи | Без когорты — `insufficient_data`; нулевые наблюдаемые продажи — нулевой результат; это наблюдения, а не прогноз | В золотом fixture 380.0000 на 10 идентифицированных клиентов |
| Сегменты RFM — `rfm` | Давность — дни до выбранной даты окончания; частота — уникальные заказы; денежный показатель — идентифицированные валовые продажи. Каждое измерение использует относительные квинтильные оценки, а FM = F + M | Менее 5 клиентов — `insufficient_data`; одинаковые значения получают одинаковую оценку, полная таблица соответствия оценок сегментам находится в реестре | Оценки относительны для этой загрузки, а не являются универсальными эталонами |
| Детализация сегментов RFM — `rfm_drilldown` | Агрегированные валовые продажи сегмента плюс фиксированные интервалы давности (от 0-30 до 366+) и частоты (1, 2, 3, 4, 5, 6-10, 11-20, 21+); без строк по клиентам | Менее 5 клиентов — `insufficient_data`; при нулевых валовых продажах доля null | Золотой fixture включает равные значения без разрешения по ID |
| Частота покупок — `purchase_frequency` | Клиенты группируются по уникальным идентифицированным заказам до выбранного конца в 1, 2, 3, 4, 5, 6-10, 11-20 и 21+ | Без идентифицированных клиентов — пустые количества, доли null и `insufficient_data` | Клиент с двумя заказами относится к интервалу 2 |
| Концентрация клиентов — `concentration` | Валовые продажи верхнего дециля / идентифицированные валовые продажи; для N клиентов верхняя группа содержит `ceil(N / 10)` крупнейших значений продаж диапазона, без разрешения равенства на границе | При менее чем 10 клиентах или нулевых идентифицированных валовых продажах — `insufficient_data` и доля null | При N=10 продажи 1000, 500 и восемь по 100 дают 1000 / 2300 = 0.4348 |

Уровни покрытия 50% и 80% включительны: ниже 50% данные скрыты; от 50.0% до, но не включая 80% показывается
предупреждение о низком покрытии; 80% и выше — норма. UI обрезает отображаемый процент до одного десятичного знака,
не округляя через границу уровня. Покрытие считается по заказам, а не по строкам. Файл без столбца означает
недоступность, а не покрытие 0%.

Идентичность клиента и когорты используют всю историю до выбранной даты окончания. Перенос начала диапазона вперед не
переклассифицирует клиента как нового и не меняет когорту. Давность RFM и зрелость когорты привязаны к выбранной дате
окончания, а не к сегодняшнему дню. Неполная или будущая ячейка когорты — **Пока не наблюдалось**, а не нулевой результат.

Правила согласованности загрузки точны: пустые значения внутри заказа заполняются его единственным непустым ID; два
разных ID отклоняют всю загрузку; заказ только с пустыми значениями остается неидентифицированным. Ограничение
`customer_id` по умолчанию — 128 символов. Проверки по мере возможности отклоняют очевидные адреса электронной почты,
телефонные номера и значения длиннее лимита; они не могут распознать имена, почтовые адреса, национальные ID,
обратимые кодировки или необычные форматы телефонов.

Данные клиента псевдонимны, а не анонимны. Используйте UUID или внутренний ключ либо хеш с секретной солью, хранящейся
вне файла. Ответы содержат только агрегированные количества и суммы: списка, поиска, скачивания или экспорта клиентов
нет, а ID клиентов, принадлежность к когорте и записи RFM не журналируются. Данные клиентов находятся только в файле
DuckDB набора данных, удаляются с ним после `DATASET_TTL_HOURS` (по умолчанию 24) или сразу после **Анализировать другой файл**;
исходный CSV удаляется после импорта. Прогнозируемая ценность клиента за 12 месяцев — отдельная будущая метрика, а не
эта наблюдаемая мера.

## Настройка

Сервер читает эти переменные окружения при запуске. Все переменные необязательны.

| Переменная | Тип | По умолчанию | Действие |
| --- | --- | --- | --- |
| `DATASET_DIR` | path | `./tmp_datasets` (`/data` в образе Docker) | Каталог с одним файлом DuckDB на набор данных. Если отсутствует, создается с приватными правами. |
| `DATASET_TTL_HOURS` | integer > 0 | `24` | Число часов до истечения и удаления набора данных. |
| `DATASET_TTL_SECONDS` | integer > 0 | unset | Только для тестов. Если задано, срок жизни в секундах вместо `DATASET_TTL_HOURS`. Браузерные тесты используют его для проверки реального истечения. Не задавайте в production. |
| `MAX_UPLOAD_BYTES` | integer > 0 | `52428800` (50 MB) | Максимальный размер загрузки в байтах. Файл большего размера отклоняется с `file_too_large`. |
| `MAX_ROWS` | integer > 0 | `500000` | Максимум строк данных (без заголовка) в загрузке. Превышение отклоняется с `too_many_rows`. |
| `CUSTOMER_ID_MAX_LENGTH` | integer > 0 | `128` | Максимальное число Unicode-символов непустого `customer_id`; более длинные значения отклоняются с `customer_id_too_long`. |
| `CLEANUP_INTERVAL_MINUTES` | integer > 0 | `15` | Частота удаления сервером истекших наборов данных (также выполняется при запуске). |
| `PUBLIC_DEMO_MODE` | boolean | `false` | `true` отключает загрузки, см. [Демонстрационный режим](#демонстрационный-режим). |
| `MAX_DATASETS` | integer > 0 | `200` | Максимум неистекших наборов на сервере. Создание еще одного (загрузка или **Попробовать пример данных**) возвращает 503 `capacity_reached`, пока один не истечет или не будет удален. |
| `RESPONSE_CACHE_MAX_ENTRIES` | integer >= 0 | `256` | Максимум закешированных ответов Overview/Product в этом процессе. `0` отключает кеш ответов. |
| `RESPONSE_CACHE_TTL_SECONDS` | integer > 0 | `300` | Максимальный срок жизни закешированного ответа Overview/Product; истечение набора данных всегда имеет приоритет. |
| `OSA_ENVIRONMENT` | `development` or `production` | `development` | Среда выполнения. Другие значения запрещают запуск. |
| `OSA_VERSION` | string | `local` | Читаемая версия. CI задаёт версию сборки; можно переопределить через `docker run -e`. |

Булевы значения принимают `true`/`false`, `1`/`0` и `yes`/`no` в любом регистре (также работают `on`/`off`,
`t`/`f` и `y`/`n`).

Недопустимое значение не дает серверу запуститься, а ошибка называет переменную. Недопустимыми считаются: не число,
ноль или отрицательное число, десятичное значение вроде `1.5`, пустая строка или булево значение вне вариантов выше.
Например, `MAX_ROWS=0 uv run uvicorn app.main:app --app-dir backend` завершается с
`MAX_ROWS  Input should be greater than 0`.

## Контракт набора данных

Одна строка — одна товарная позиция в завершенном заказе. Файл должен содержать шесть обязательных столбцов и один
необязательный (та же таблица показана на экране загрузки). Значение и ограничения конфиденциальности `customer_id`
описаны в [Аналитике клиентов](#аналитика-клиентов):

| Столбец | Тип | Правило |
| --- | --- | --- |
| `order_id` | String | Обязателен и не пуст. Используется для подсчета уникальных заказов. |
| `order_date` | Date | Обязательная календарная дата ISO в формате `YYYY-MM-DD`. Не должна быть в будущем. |
| `product_id` | String | Обязателен и не пуст. Идентифицирует товар. |
| `product_name` | String | Обязательно и не пусто. Один `product_id` должен соответствовать ровно одному названию в загрузке. |
| `quantity` | Integer | Обязательно и больше нуля. Нулевое и отрицательное количество недопустимо. |
| `unit_price` | Decimal | Обязательна и неотрицательна. Нулевая цена принимается с предупреждением; отрицательная недопустима. |
| `customer_id` | String | Необязателен. Допускается пустое значение; не более `CUSTOMER_ID_MAX_LENGTH` Unicode-символов (по умолчанию 128); используйте хешированный идентификатор, UUID или неличный внутренний ключ. Никогда не используйте адрес электронной почты, телефон, имя или другой прямой идентификатор. |

Правила на уровне файла:

- UTF-8, разделитель — запятая, одна строка заголовка. Заголовок считается строкой 1 в отчетах об ошибках, поэтому
  первая строка данных — строка 2.
- Имена столбцов сопоставляются после удаления окружающих пробелов. Порядок не важен. Столбец, который не является
  одним из шести обязательных или `customer_id`, игнорируется с предупреждением (`extra_column`).
- `(order_id, product_id)` уникальна: один товар встречается в заказе не более одного раза.
- Одно название на `product_id` во всем файле.
- Внутри заказа пустые `customer_id` заполняются его единственным непустым ID; конфликтующие ID отклоняют загрузку,
  а заказы только с пустыми значениями остаются неидентифицированными.
- Одна валюта на загрузку, выбирается в форме загрузки (см. [Валюты](#валюты)).
- Любая недопустимая строка отклоняет весь файл. Ничего не сохраняется.
- По умолчанию не более 50 MB и 500,000 строк (переменные `MAX_UPLOAD_BYTES` и `MAX_ROWS`).
- Количество — целое число до 2,147,483,647. Цена — обычное десятичное число (без символа валюты и разделителя тысяч)
  максимум с 14 цифрами до и 4 после точки.

### Допустимый пример

Сохраните это как `example.csv`. В файле три строки и два заказа; заказ `A-1001` содержит две строки.

```csv
order_id,order_date,product_id,product_name,quantity,unit_price
A-1001,2025-03-01,P-10,Ceramic Mug,2,12.50
A-1001,2025-03-01,P-20,Travel Tumbler,1,24.00
A-1002,2025-03-02,P-10,Ceramic Mug,1,12.50
```

Можно добавить необязательный `customer_id`; допускаются пустые ячейки:

```csv
order_id,order_date,product_id,product_name,quantity,unit_price,customer_id
A-1001,2025-03-01,P-10,Ceramic Mug,2,12.50,CUST-007
A-1001,2025-03-01,P-20,Travel Tumbler,1,24.00,
```

Когда приложение работает на порту 8000, импортируйте файл через API:

```sh
curl -F currency=USD -F file=@example.csv http://localhost:8000/api/datasets
```

Ответ — `201` с `"warnings":[]`, `dataset_id`, `token` и первой сводкой. Валовые продажи здесь равны 61.50 по
2 заказам и 4 единицам.

### Недопустимые примеры

Каждый пример — небольшое изменение допустимого файла. Приложение отвечает `422` с кодом ошибки `validation_failed`
и списком ошибок; поле `code` каждой ошибки приведено в таблице. Ошибка также содержит номер строки и столбец.

| Изменение допустимого файла | `code` ошибки | Строка |
| --- | --- | --- |
| Удалить `unit_price` из заголовка (и последнее значение каждой строки) | `missing_column` | нет (уровень файла) |
| Изменить дату `2025-03-02` на `2025-13-02` | `invalid_date` | 4 |
| Изменить количество последней строки с `1` на `0` | `invalid_quantity` | 4 |
| Повторить последнюю строку | `duplicate_line` | 5 |

### Коды ошибок

Отчет перечисляет первые 100 ошибок и сообщает общее число (`error_count`).

| Код | Причина |
| --- | --- |
| `file_too_large` | Файл больше `MAX_UPLOAD_BYTES`. |
| `empty_file` | Файл пуст. |
| `invalid_encoding` | Файл не является корректным UTF-8. |
| `malformed_csv` | Файл невозможно прочитать как CSV (например, одно поле длиннее 131,072 символов). |
| `too_many_rows` | Более `MAX_ROWS` строк данных. |
| `no_data_rows` | Заголовок есть, строк данных нет. |
| `missing_column` | Один из шести обязательных столбцов отсутствует в заголовке. |
| `duplicate_column` | Обязательный столбец встречается в заголовке более одного раза. |
| `missing_value` | Обязательное значение пусто. |
| `invalid_date` | `order_date` не является реальной датой в формате `YYYY-MM-DD`. |
| `future_date` | `order_date` позже сегодняшней даты (UTC). |
| `invalid_quantity` | `quantity` не является целым числом от 1 до 2,147,483,647. |
| `invalid_price` | `unit_price` не является обычным десятичным числом максимум с 14 цифрами до и 4 после точки. |
| `negative_price` | `unit_price` меньше нуля. |
| `line_total_too_large` | `quantity × unit_price` равно 100,000,000,000,000 или больше и выходит за точный десятичный диапазон валовых продаж. |
| `malformed_row` | В строке другое число значений, чем в заголовке. |
| `duplicate_line` | Те же `order_id` и `product_id` встречались в предыдущей строке. |
| `conflicting_product_name` | Одному `product_id` соответствуют разные `product_name`. |
| `conflicting_customer_id` | В одном заказе больше одного непустого `customer_id`. |
| `customer_id_too_long` | Непустой `customer_id` превышает `CUSTOMER_ID_MAX_LENGTH` Unicode-символов. |
| `customer_id_looks_like_email` | Непустой `customer_id` соответствует очевидному шаблону электронной почты. |
| `customer_id_looks_like_phone` | Непустой `customer_id` соответствует очевидному шаблону телефона. |

Три проверки `customer_id` — защитная мера по мере возможности, а не анонимизация или гарантия соответствия требованиям.
Проверка электронной почты ищет `[^@\s]+@[^@\s]+\.[A-Za-z]{2,}` в любом месте значения. Проверка телефона допускает
только цифры, пробелы, `+ - . ( )`, от 7 до 15 цифр и требует либо начальный `+`, либо видимые пробелы/скобки, либо
не менее двух разделителей `-`/`.`. У этих эвристик намеренно есть известные пропуски: телефон только из цифр вроде
`05321234567` принимается, а группы цифр с двумя дефисами вроде `2024-01-000123` отклоняются. Принятый ID не становится
от этого анонимным.

Запрос также может завершиться до чтения файла: валюта вне списка возвращает `400 invalid_request`.

### Покрытие клиентов

Если присутствует `customer_id`, покрытие один раз вычисляется при импорте на уровне заказов, после заполнения пустых
ID из другой строки того же заказа:

`identified distinct orders / all distinct orders`

Это не процент строк, поэтому идентифицированный заказ из пяти строк учитывается один раз. Метаданные набора данных
сообщают количества и округленное отношение, а уровень определяется по точным целым количествам для всего набора:

- ниже 50%: `suppressed`; аналитика клиентов недоступна;
- от 50% до, но не включая 80%: `warning`; аналитика клиентов доступна с предупреждением о низком покрытии;
- 80% и выше: `normal`; аналитика клиентов доступна как обычно.

Файлы без `customer_id` имеют уровень `missing` и `coverage: null`, а не нулевое покрытие. Метаданные покрытия содержат
только количества и никогда не содержат ID клиентов. Покрытие диапазона дат использует ту же формулу уровня заказов
с включительными датами; пустой диапазон имеет нулевые количества и `coverage: null`. Уровень остается основанным на
всем наборе, поэтому фильтрация дат не заставляет модуль Customers появляться или исчезать.

### API клиентов

`GET /api/datasets/{id}/customers` защищен bearer-токеном и принимает те же необязательные параметры запроса `start`,
`end` и `comparison`, что и конечные точки модулей Overview и Products. Без параметров используется полный набор и
сравнение `previous_period` по умолчанию. Недопустимые, обратные или выходящие за диапазон даты возвращают
`400 invalid_range`; неизвестное сравнение — `400 invalid_request`. Отсутствующие или неверно оформленные учетные
данные возвращают `401 unauthorized` с `WWW-Authenticate: Bearer`; неизвестный, истекший или удаленный набор —
`404 not_found`.

Типизированный ответ содержит `module`, `range`, `comparison`, `currency`, `availability`, `coverage` и `sections`.
`coverage.dataset` — сохраненное покрытие всего набора, а `coverage.range` — покрытие выбранного включительного диапазона;
оба содержат уровень, округленное отношение и количество идентифицированных, неидентифицированных и всех заказов.
При нормальном или предупреждающем покрытии `sections.identified_customers` сообщает число уникальных
идентифицированных клиентов с активностью во включительном диапазоне, а также общие поля сравнения и изменения.
Пустая активная группа имеет состояние `zero_result`. `sections.new_vs_returning` делит идентифицированные валовые
продажи диапазона на продажи новых клиентов (строки с датой первой покупки клиента) и вернувшихся (более поздние строки)
с теми же полями сравнения; классификация всегда использует `first_order_date` из всей загрузки, поэтому перенос начала
диапазона не превращает вернувшегося клиента в нового.

`sections.days_between_purchases` сообщает интервалы повторных заказов только для текущего диапазона (полей сравнения
нет). Уникальные заказы каждого идентифицированного клиента датируются первой строкой и сортируются; каждая
последовательная пара дает интервал в календарных днях, два заказа в один день дают `0`. Интервал учитывается, если
поздний заказ входит во включительный диапазон, даже если ранний предшествует началу; заказы после конца игнорируются.
Раздел возвращает `median_days` (среднее двух центральных значений при четном количестве, поэтому возможно окончание
`.5`; среднее арифметическое в целом не сообщается), `interval_count`, `contributing_customers` и девять фиксированных
`buckets` (`0`, `1-7`, `8-14`, `15-30`, `31-60`, `61-90`, `91-180`, `181-365`, `366+` дней), каждый со своим
`interval_count` и `share` всех интервалов. Без включенных интервалов медиана и все доли равны `null`, состояние —
`insufficient_data`.

`sections.cohort_retention` — месячная матрица удержания когорт привлечения только для текущего диапазона (без полей
сравнения). Когорта клиента — месяц его первого заказа за всю историю; строки — месяцы когорт от месяца начала до
месяца конца диапазона, от старого к новому, поэтому изменение только начала никогда не меняет строку. Конец диапазона
— `data_cutoff`: клиенты, впервые появившиеся после него, не входят в группу, а более поздняя активность игнорируется;
активность до начала по-прежнему учитывается. Каждая строка содержит `cohort_month` (`YYYY-MM`), `cohort_size`,
`complete_months` и `cells`; месяц `N` (0 = месяц привлечения) содержит `retained_count` (участники с
идентифицированной строкой в этом календарном месяце) и `retention` (`retained_count / cohort_size`). Состояние ячейки:
`state` имеет значение `complete` (месяц целиком не позже отсечения), `partial` (месяц содержит отсечение; количество на текущий момент) или
`not_observed` (месяц начинается после отсечения; значения `null`, а не `0`). Строки дополняются до ширины старейшей
когорты. Без пересекающейся когорты `rows` пуст и состояние — `insufficient_data`.

`sections.historical_customer_value` сообщает наблюдаемую историческую ценность клиента (уже наблюдаемые валовые
продажи, не прогноз) только для текущего диапазона. Группа состоит из участников строк `cohort_retention`; ценность
клиента — его идентифицированные валовые продажи с датой не позже `data_cutoff` (конца диапазона), включая продажи до
начала. Возвращаются `customer_count`, `average` (общая ценность / `customer_count`) и `median` (среднее двух центральных
значений при четном количестве), денежные значения округляются half-up до 4 знаков. `rows` повторяет строки
`cohort_retention` и состояния ячеек, где `value_per_customer` = накопленные валовые продажи когорты до конца месяца
`N` (ограниченные отсечением) / `cohort_size` (`null` для `not_observed`). `all_cohorts` содержит одну точку на смещение
месяца по когортам с ячейкой `complete` (`value_per_customer`, `contributing_cohorts`; `null` и `0`, когда завершенных
нет). Без когорты состояние — `insufficient_data`; участники с общей ценностью `0` дают `zero_result` со значениями `0.0000`.

`sections.rfm` сообщает количества сегментов RFM только для текущего диапазона, без сравнения. Группа (`customer_count`,
N) — идентифицированные клиенты с идентифицированным заказом не позже конца диапазона; учитывается вся их
идентифицированная активность до конца, начало диапазона ни на что не влияет. Давность — число дней от последней
идентифицированной строки клиента до `recency_anchor` (конца диапазона), частота — уникальные заказы, денежный показатель
— валовые продажи. Каждое измерение оценивается от 1 до 5 по рангу клиента:
`floor(5 × (2 × worse + ties) / (2 × N)) + 1`, где `worse` — число клиентов со строго худшим значением, а `ties` — с
таким же; равные значения получают равные оценки, постоянное измерение — 3. При `FM = F + M` первое подходящее правило
задает сегмент: Champions (R ≥ 4, FM ≥ 8), Loyal (R ≥ 3, FM ≥ 6), Potential Loyalists (R ≥ 4, FM ≤ 5), Needs Attention
(R = 3, FM ≤ 5), At Risk (R ≤ 2, FM ≥ 6), Lost (R ≤ 2, FM ≤ 5). `segments` всегда перечисляет все шесть в этом
порядке с `customer_count` и `share`; оценки клиентов не покидают backend. Менее 5 клиентов дает пустой `segments` и
`insufficient_data`. Фиксированное `note` говорит, что сегменты относительны для клиентской базы этой загрузки, а не
являются универсальными эталонами.

`sections.rfm_drilldown` сообщает агрегированные показатели по сегментам RFM с той же группой, входными данными и
сегментами, что `sections.rfm`, без сравнения. На верхнем уровне возвращаются `customer_count` (N, то же, что в
`sections.rfm`), `recency_anchor` (конец диапазона) и `gross_sales` (суммарный денежный показатель всех N клиентов до
конца, округленный half-up до 4 знаков). `segments` всегда перечисляет все шесть сегментов в порядке `sections.rfm`;
каждый содержит `customer_count`, `gross_sales` (сумму денежных значений участников), `gross_sales_share` (`gross_sales`
сегмента / верхнеуровневые `gross_sales`, `null` при нулевом итоге), `recency_distribution` по шести фиксированным
интервалам дней до привязки (`0-30`, `31-60`, `61-90`, `91-180`, `181-365`, `366+`; `key`, `min_days`, `max_days`,
`customer_count`) и `frequency_distribution` по восьми фиксированным интервалам уникальных заказов (`1`, `2`, `3`,
`4`, `5`, `6-10`, `11-20`, `21+`; `key`, `min_orders`, `max_orders`, `customer_count`). У открытых интервалов максимум
равен `null`, пустые сегменты и интервалы — `0`. Сегмент с одним участником сообщается как любой другой, поскольку ID
или оценка клиента не возвращаются. Менее 5 клиентов дает `insufficient_data` с реальными `customer_count` и
`gross_sales` и пустым списком `segments`.

Отсутствующее или скрытое покрытие исключает все разделы (`sections` пуст). Конечная точка всегда возвращает
`Cache-Control: no-store`. Ответы о клиентах по своей конструкции содержат только агрегаты: они никогда не возвращают
ID клиентов, объекты уровня клиента, поиск, детализацию, скачивание или экспорт, а идентификаторы не пишутся в журналы.

### Предупреждения

Предупреждения не отклоняют файл. Они возвращаются в списке `warnings` ответа `201` и на экране загрузки.

| Код | Значение |
| --- | --- |
| `extra_column` | В файле есть столбец, не входящий в шесть обязательных и не являющийся `customer_id`, например `note`. Он игнорируется и не сохраняется. |
| `zero_price` | У одной или нескольких строк цена единицы равна 0. Они импортируются и учитываются как заказы и единицы, но не дают валовых продаж. |

## Интервалы тренда

Тренд группирует валовые продажи по календарным интервалам. Гранулярность зависит только от выбранного диапазона с
обеими включенными конечными датами: до 90 дней — по дням, свыше 90 до 730 дней — по неделям, дольше — по месяцам.
API возвращает `bucket_start` для каждого интервала (его первый день) без поля покрытия.

- Диапазон включителен: в него входят и дата начала, и дата окончания.
- Неделя идет с понедельника по воскресенье; `bucket_start` недельного интервала — понедельник. Месяцы календарные.
- Интервал, обрезанный диапазоном (первая неделя/месяц начинается до даты начала либо последняя заканчивается после
  даты окончания), является неполным периодом. Диаграмма определяет это по диапазону и календарю, поэтому день без
  продаж все равно считается покрытым. Однодневный дневной интервал всегда полный (данные содержат только даты);
  однодневный срез недели или месяца неполон. Диапазон внутри одной недели или месяца показывает этот интервал неполным.
- Для неполного периода подпись оси показывает покрытые даты (`29–31 дек.`, `10–31 мар. 2025 г.`), а не `Неделя с 29 дек.`
  или название месяца; точка пустая, под диаграммой есть примечание, а подсказка добавляет год и
  `Неполный период: <охваченные даты>`. У полного интервала этого нет.
- Суммируются только строки внутри диапазона, поэтому неполный интервал содержит продажи только покрытых дат.

## Валюты

Валюта выбирается в форме загрузки: USD, EUR, GBP, TRY, CAD, AUD, JPY, CHF, SEK, PLN. Это лишь подпись денежных сумм.
Конвертации и обменного курса нет. Любой другой код отклоняется с `400 invalid_request`.

## Конфиденциальность

- Исходный CSV удаляется сразу после завершения импорта как при успехе, так и при ошибке.
- Обязательные столбцы и необязательный `customer_id` хранятся в одном файле DuckDB на набор данных в `DATASET_DIR`
  с приватными правами (`0600` для файла, `0700` для каталогов).
- ID клиентов являются псевдонимными данными, а не анонимными. Они хранятся в течение 24-часового срока жизни набора.
  Используйте хешированный идентификатор, UUID или неличный внутренний ключ; никогда не загружайте прямой идентификатор,
  например адрес электронной почты, телефон или имя.
- Проверки длины, электронной почты и телефона для ID клиента — лишь защитные меры по мере возможности. Это не
  анонимизация и не гарантия соответствия требованиям; автоматические проверки не находят все виды персональных данных.
- Набор данных удаляется после `DATASET_TTL_HOURS` (по умолчанию 24) при очистке во время запуска и затем каждые
  `CLEANUP_INTERVAL_MINUTES` либо сразу после нажатия **Анализировать другой файл**.
- Успешные ответы модулей могут храниться в ограниченном локальном для процесса кеше в течение
  `RESPONSE_CACHE_TTL_SECONDS` (по умолчанию 300 секунд); авторизация выполняется при каждом запросе, ключи учитывают
  набор и параметры, а истечение или удаление удаляет закешированные ответы набора. Кеш не разделяется между экземплярами.
- Для доступа нужен случайный bearer-токен. Браузер хранит его в `sessionStorage`, поэтому он исчезает при закрытии
  вкладки. Сервер хранит только его SHA-256-хеш.
- Отсутствующий или истекший ID набора дает 404, а неверный токен существующего набора — 401, поэтому статус показывает,
  существует ли ID. Это принятый риск: ID являются случайными 128-битными значениями, которые невозможно угадать, а
  без токена набор остается недоступным.
- В журнале на каждый запрос записывается одна строка JSON с методом, путем, статусом, длительностью и ID набора данных.
  ID намеренно журналируется для трассировки запроса; он не является секретом и бесполезен без токена. Журналы никогда
  не содержат токены, содержимое и имена файлов, названия товаров или ID заказов. Журналы ошибок содержат имена классов
  исключений и кадры стека, но не сообщения исключений.
- Ничего не отправляется другим сервисам.
- Если предоставлены ID клиентов, файл DuckDB набора также содержит `customer_facts`: по одной строке на
  идентифицированного клиента с датами первого/последнего заказа за всю историю, месяцем привлечения, уникальными
  заказами, единицами и валовыми продажами за весь срок. Строк для неидентифицированных заказов нет; таблица истекает
  вместе с набором и не является отдельной общей базой данных.

## Демонстрационный режим

Размещенное демо — общедоступный экземпляр с `PUBLIC_DEMO_MODE=true`: посетители могут изучать только встроенные
тестовые данные и не могут загружать файл. Его наборы истекают как любые другие (`DATASET_TTL_SECONDS`), а работает он
в одном экземпляре. Чтобы анализировать свои файлы, [запустите приложение самостоятельно](#запуск-с-docker).

`PUBLIC_DEMO_MODE=true` предназначен для общедоступного сервера, который не должен принимать чужие файлы:

- `POST /api/datasets` отвечает 403 `upload_disabled` без чтения тела.
- **Попробовать пример данных** и скачивание примера продолжают работать.
- Экран загрузки показывает только формат файла и **Попробовать пример данных**, без полей файла и валюты. Он сообщает, что
  принимает только тестовые данные, и ссылается на [Запуск с Docker](#запуск-с-docker) для загрузок.
- `GET /api/config` возвращает `{"public_demo_mode":true,...}` — так экран узнает режим.
- `MAX_DATASETS` защищает диск общедоступного сервера: каждое нажатие **Попробовать пример данных** создает набор, а при
  достижении лимита возвращается 503 `capacity_reached`.

## Ограничения

- Только один экземпляр. Горизонтального масштабирования нет: наборы данных — файлы на диске этого экземпляра.
- Переживание перезапуска обеспечивается по мере возможности и только если `DATASET_DIR` находится в томе.
- Нет учетных записей и общего доступа. Набор доступен только с токеном, который остается в одной вкладке браузера.
- Одна валюта на файл.
- Списки, экспорт и поиск на уровне клиентов отсутствуют; показатели клиентов охватывают только идентифицированные заказы.
- Только валовые продажи: без возвратов, скидок, налогов или доставки.
- По умолчанию 50 MB и 500,000 строк.
- Ширина для телефонов, планшетов и компьютеров (от 360 px); широкие таблицы прокручиваются внутри собственной области
  (см. [`_docs/design-system.md`](_docs/design-system.md)).

## Архитектура

Frontend React (Vite) с Recharts обменивается JSON с backend FastAPI. Каждый набор — один файл DuckDB в `DATASET_DIR`;
проверка и аналитика выполняются SQL-запросами к нему. Канонический импорт создает переиспользуемые `order_facts`,
`product_facts` и, при наличии идентифицированных данных клиентов, `customer_facts` за всю историю в том же файле.
Фоновая задача внутри процесса удаляет истекшие наборы. Образ Docker — один контейнер, где FastAPI обслуживает API и
собранный frontend с одного origin на порту 8000. См. [руководство по архитектуре Phase 3](_docs/architecture.ru-RU.md),
[каталог метрик](_docs/metrics.ru-RU.md), [контрольный список выпуска и отчет о доказательствах](_docs/phase-3-release-checklist.md),
[спецификацию Phase 3](_docs/open_sales_analytics_phase_3_spec.md) и [бэклог](_docs/tasks.md).

### Обязательные проверки CI

Для слияния в `main` предполагается обязательное прохождение этих четырех проверок с точными именами, которые GitHub
показывает в pull request (Settings, Branches или Rules, “Require status checks to pass”, затем выберите каждое имя):

- `Backend (tests, ruff, mypy)`
- `Frontend (tests, lint, type check, build)`
- `Dependency scan (Python, npm) / Dependency scan (Python, npm)`
- `Container (build, smoke, browser tests)`

Сканирование зависимостей вызывает переиспользуемый workflow `.github/workflows/dependency-scan.yml`, поэтому GitHub
показывает его имя дважды как `<calling job> / <called job>`. В защите ветки выберите полное удвоенное имя; простое
`Dependency scan (Python, npm)` не соответствует запуску проверки. Если вы переименуете задание в
`.github/workflows/`, обновите этот список и настройку защиты в том же изменении, поскольку обязательная проверка,
которой больше нет, блокирует любое слияние. Сравните с `gh pr checks <number>` в любом pull request.

### Сканирование зависимостей

CI сканирует оба lock-файла в каждом pull request и при каждом push в `main`, а также каждый понедельник в 05:17 UTC
(`.github/workflows/dependency-scan-scheduled.yml`), поэтому новая уязвимость в неизменившемся lock-файле делает запуск
красным, не дожидаясь следующего pull request. Оба вызывают одно общее определение
`.github/workflows/dependency-scan.yml`, поэтому команды и политика ниже одинаковы. Запланированный запуск имеет
`contents: read`, не получает секретов и также может быть запущен вручную на вкладке Actions (“Run workflow”).

| Экосистема | Инструмент и входные данные | Условие сбоя CI |
| --- | --- | --- |
| Python | `pip-audit` по `uv.lock` (runtime- и dev-пакеты) | любая известная уязвимость (pip-audit не имеет фильтра серьезности) |
| npm | `npm audit --audit-level=high` по `frontend/package-lock.json` | рекомендации high и critical; low и moderate видны в журнале, но не вызывают сбой |

Ошибка сканера (нет сети, неверные данные) также проваливает задание: в шагах нет `|| true` и `continue-on-error`.
Списка игнорирования нет. Если исправления для рекомендации еще нет, выход — проверенный pull request, который
закрепляет исключение в команде сканирования с ID рекомендации и причиной рядом (`pip-audit --ignore-vuln ID` или
удаление пакета); это никогда не должно быть молчаливым пропуском. В кеше хранятся только скачанные пакеты и браузер
Playwright; наборы данных, загрузки, секреты и файлы DuckDB не кешируются и не загружаются как артефакты.

Dependabot (`.github/dependabot.yml`) по понедельникам открывает pull request для устаревших зависимостей Python
(`uv.lock`, из `pyproject.toml`) и npm (`frontend/package-lock.json`), не более 5 открытых на экосистему. Dependabot
обновляет только существующие зависимости и никогда не добавляет новые. Его pull request проходят тот же CI без
секретов (pull request Dependabot получают токен только для чтения), поэтому сканирование, тесты, сборка и браузерный
набор выполняются с обновленным lock-файлом. Проверяйте их как обычное изменение: прочитайте заметки о выпуске и diff
lock-файла, сливайте только при всех зеленых проверках, а при повышении major-версии также один раз запустите приложение
вручную. Красная проверка — повод закрыть или исправить pull request, но не сливать его.

Неудачный запланированный запуск отображается красным запуском “Dependency scan (scheduled)” на вкладке Actions
репозитория (фильтр по имени workflow или `event:schedule`). GitHub также отправляет владельцу репозитория письмо: для
запланированных workflow уведомление получает пользователь, последним изменивший строку `cron`, поэтому если расписание
редактировал кто-то другой, проверьте, включены ли его уведомления (Settings, Notifications, Actions). Запланированные
workflow выполняются только в ветке по умолчанию, и GitHub приостанавливает их после 60 дней без активности репозитория;
в этом случае снова включите workflow на вкладке Actions.

### Закрепление образов контейнера

Решение: базовые образы в `Dockerfile` (`node:26`, `python:3.14-slim`) закреплены по digest
(`FROM image:tag@sha256:...`, digest мультиархитектурного индекса). Причина: тег перемещается, поэтому две сборки одного
коммита могут отличаться, а непроверенное изменение upstream может сломать или скомпрометировать сборку; digest делает
сборку воспроизводимой, а каждое изменение базового образа — проверяемым pull request. Dependabot (запись `docker` в
`.github/dependabot.yml`, по понедельникам) обновляет тег и digest вместе, а задание CI `docker-smoke` собирает и
запускает контейнер с новым образом до слияния. Для ручного обновления найдите digest нужного тега и замените обе части
строки `FROM`. Образ `uv`, копируемый через `COPY --from=ghcr.io/astral-sh/uv:0.8`, пока остается на своем теге.

### Закрепленные actions

Задание `pinned-actions` в `.github/workflows/ci.yml` завершается ошибкой, если любой `uses:` в `.github` не является
локальным путем (`./.github/workflows/...`) или `owner/repo@<40 hex characters>`; аннотация ошибки называет файл и
строку. Пишите закрепления как `uses: owner/repo@<sha> # vX.Y.Z`; Dependabot поддерживает SHA и комментарий актуальными.
Проверка — shell-шаг с `contents: read`, без секретов и сторонних action кроме `actions/checkout`, поэтому она также
выполняется для pull request из fork и от Dependabot.

### Браузерный тест

Небольшой набор Playwright (Chromium, `frontend/e2e/`) охватывает основные сценарии: Try sample data, допустимую и
недопустимую загрузку, диапазон дат и Reset, Analyze another file, межмодульный сценарий клиентов, адаптивные макеты
при 360/768/1280 px и истекший набор данных.
Один раз установите браузер (около 150 MB, хранится вне репозитория), затем запустите из `frontend/`:

```sh
npx playwright install chromium
npx playwright install-deps chromium   # Linux only: system libraries, needs sudo; CI runs it too
npm run e2e
```

`npm run e2e` сам запускает backend (порт 8000) и dev-сервер Vite (порт 5173) с временным каталогом наборов данных, а
затем останавливает их. Оба порта должны быть свободны. Для тестирования уже работающего приложения (например,
контейнера) задайте `E2E_BASE_URL`; сервер запускаться не будет. Приложение должно работать с
`DATASET_TTL_SECONDS=60`, поскольку сценарий истечения ожидает реального истечения с ограниченным опросом:

```sh
docker build -t open-sales-analytics .   # from the repository root
docker run -d --name oca -p 8000:8000 -e DATASET_TTL_SECONDS=60 open-sales-analytics
curl -f http://localhost:8000/api/health   # answers {"status":"ok"}; repeat for a few seconds until it does
curl -f http://localhost:8000/d/anything | grep -i '<div id="root"'   # the single-page app
E2E_BASE_URL=http://localhost:8000 npm run e2e
docker rm -f oca
```

При сбое trace и снимок экрана сохраняются в `frontend/test-results/` (откройте trace командой
`npx playwright show-trace`). При установленном `CI` (как в GitHub Actions) trace не записывается, поскольку содержит
сетевые ответы, а CI загружает только снимки сбоев.
